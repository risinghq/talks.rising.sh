```bash
mkdir proyecto1 && cd proyecto1
```

Esto crea un `pyproject.toml`, el archivo que describe el proyecto y sus dependencias. Cada proyecto en su propio directorio evita mezclar archivos.


- gunicorn: servidor de producción
- psycopg2-binary: conector para PostgreSQL

Así desarrollo y producción usan la misma base.

</Col>

Esto crea la base de datos inicial que Django necesita para usuarios, sesiones y otros componentes internos. Forma parte de la plantilla de Django; no vamos a tocar bases de datos todavía.

<Section>Herramienta #1: Docker</Section>

<Content title="Docker" subtitle="¿Por qué usarlo?">

<Columns>
<Col>

**Sin Docker:**

- Configurar manualmente cada servidor
- Instalar dependencias (Python, nginx, etc.)
- Ajustar según el sistema operativo
- Inconsistencias entre entornos
- "Funciona en mi máquina, pero no en producción"

</Col>
<Col>

**Con Docker:**

- Empaquetas la app junto con sus dependencias
- La misma imagen funciona en cualquier entorno
- Despliegues consistentes
- Aislamiento entre aplicaciones

</Col>
</Columns>

<Callout title="¡No te abrumes!">

No necesitas instalar Docker en tu máquina: consume bastantes recursos y las imágenes necesarias ya están en Docker Hub. Tampoco memorices cada comando. Lo importante es entender **qué parámetros ajustar y cuándo**; tu Dockerfile será muy similar entre proyectos.

</Callout>

</Content>

<Content title="Docker" subtitle="Conceptos básicos">

**Imagen**: paquete inmutable con tu aplicación, sus dependencias, la configuración y el sistema operativo base. Se construye una vez con `docker build`.

**Contenedor**: instancia ejecutable de una imagen. Cada `docker run` crea un contenedor nuevo, y puedes tener varios de la misma imagen.

**Dockerfile**: archivo de texto con las instrucciones para construir una imagen paso a paso.

<Figure src={docker} alt="Un Dockerfile se construye en una imagen, y la imagen se ejecuta como contenedores" />

</Content>

<Content title="Docker" subtitle="El Dockerfile">

<Columns split="5fr 2fr">
<Col>

```dockerfile
FROM python:3.14-slim
COPY --from=ghcr.io/astral-sh/uv:0.13.6 /uv /bin/

# Puerto de la aplicación y entorno virtual que crea uv
ENV PORT=8080
ENV PATH="/app/.venv/bin:$PATH"

# Carpeta de trabajo dentro del contenedor
WORKDIR /app

# Instalar las versiones exactas de uv.lock
COPY pyproject.toml uv.lock /app/
RUN uv sync --locked --no-dev

# Copiar el proyecto
COPY . /app

EXPOSE ${PORT}
CMD ["gunicorn", "proyecto1.wsgi:application", "--bind", "0.0.0.0:8080"]
```

</Col>
<Col>

Cada línea es una capa. Docker cachea cada capa para acelerar los siguientes builds.

Crea también un archivo `.dockerignore` con la línea `.venv`, para que `COPY . /app` no copie tu entorno local encima del que instaló uv.

</Col>
</Columns>

</Content>

<Content title="Docker" subtitle="Comandos del Dockerfile">

| Comando | Descripción |
| --- | --- |
| `FROM` | Imagen base del sistema operativo y runtime. Ejemplo: `python:3.14-slim` |
| `WORKDIR` | Directorio de trabajo dentro del contenedor. Lo crea si no existe |
| `ENV` | Variables de entorno disponibles durante el build y la ejecución |
| `COPY` | Copia archivos desde tu máquina al contenedor. Ejemplo: `COPY . /app/` |
| `RUN` | Ejecuta comandos durante la construcción. Ejemplo: `uv sync --locked` |
| `CMD` | Comando que se ejecuta al iniciar el contenedor. Solo puede haber uno |
| `EXPOSE` | Documenta el puerto que usa la aplicación. No lo publica automáticamente |

</Content>

<Content title="Docker" subtitle="Build vs runtime">

<Columns>
<Col>

**Build time** (`docker build`):

- Se ejecutan: `FROM`, `WORKDIR`, `COPY`, `RUN`, `ENV`
- Resultado: una imagen inmutable
- Se ejecuta una vez (o cuando cambias el Dockerfile)
- Usa la caché de capas para acelerar

</Col>
<Col>

**Runtime** (`docker run`):

- Se ejecuta: `CMD`
- Resultado: un contenedor en ejecución
- Cada `docker run` crea un contenedor nuevo
- El contenedor se detiene cuando termina el proceso de `CMD`

</Col>
</Columns>

</Content>

<Content title="Docker" subtitle="Comandos">

<Columns>
<Col>

Con el Dockerfile listo, construye la imagen:

```bash
docker build -t proyecto1-ec2:latest .
```

Y ejecuta el contenedor:

```bash
docker run -d -p 8000:8080 proyecto1-ec2:latest
```

Esto enlaza el puerto 8080 del contenedor con el puerto 8000 de tu máquina: la aplicación queda en [http://localhost:8000](http://localhost:8000).

</Col>
<Col>

Para detener el contenedor:

```bash
docker ps
docker kill <container_id>
```

</Col>
</Columns>

</Content>

<Content title="AWS CLI" subtitle="Guardar la URI del repositorio">

<Callout title="Importante">

Guarda el valor **repositoryUri** completo: lo usarás en varios pasos. Guárdalo como variable de entorno:

```powershell
$env:ECR_REPO_URI="***.dkr.ecr.us-east-2.amazonaws.com/proyecto1-ec2"
$env:TF_VAR_ecr_repo_url=$env:ECR_REPO_URI
```

</Callout>

`ECR_REPO_URI` sirve para los comandos de Docker que siguen. `TF_VAR_ecr_repo_url` le pasa el mismo valor a Terraform, que lo usará al crear el servidor.

</Content>

<Content title="AWS CLI" subtitle="Subir nuestra imagen Docker a ECR">

Inicia sesión en el repositorio de ECR:

```powershell
aws ecr get-login-password --region us-east-2 | docker login --username AWS --password-stdin $env:ECR_REPO_URI
```

Etiqueta la imagen:

```powershell
docker tag proyecto1-ec2:latest "$($env:ECR_REPO_URI):latest"
```

Sube la imagen al repositorio:

```powershell

```

Puede tomar un par de minutos. Puedes ir por un café o tomar un descanso.

<Section>Herramienta #3: Terraform</Section>

<Content title="Terraform" subtitle="¿Por qué lo vamos a usar?">

Imagina que configuraste tu aplicación Django _manualmente_ en AWS:

- Hiciste clic en 47 botones diferentes en la consola
- Configuraste redes, subnets, security groups…
- Todo funcionó perfectamente

Genial, **pero ahora necesitas:**

- Replicarlo en producción (a escala: varias regiones, cuentas e instancias)
- Que tu compañero de trabajo configure su entorno
- Documentar qué hiciste exactamente para repetir el proceso

<Callout>

Lo más probable es que hayas olvidado qué hiciste en el paso 23. Tu compañero configurará algo distinto y, sin darse cuenta, generará inconsistencias o errores difíciles de detectar y corregir (deuda técnica).

</Callout>

</Content>

<Content title="Terraform" subtitle="La solución es Infraestructura como Código (IaC)">

Terraform define y gestiona tu infraestructura con archivos **.tf**. Un ejemplo mínimo:

```hcl
resource "aws_instance" "web" {
  ami           = "ami-0c101f26f147fa7fd"   // ID de la imagen de Amazon Linux 2023
  instance_type = "t3.micro"                // 1GB RAM, 2 vCPUs
}
```

**Ventajas:**

- El mismo código genera el mismo resultado en AWS, Google Cloud, Azure, etc.
- Se versiona con Git: ves qué cambió, cuándo y por qué (útil ante bugs o rollbacks)
- La infraestructura se replica en segundos (no en 435345 clics) con `terraform apply`
- El código ES la documentación

Descárgalo desde la [guía de instalación de Terraform](https://developer.hashicorp.com/terraform/tutorials/aws-get-started/install-cli#install-terraform).

</Content>

<Content title="Terraform" subtitle="Componentes de AWS">

Desplegar significa crear la infraestructura donde vivirá tu aplicación. Piénsalo como construir un edificio: no puedes construir sin terreno, y en AWS pasa lo mismo.

<Columns>
<Col>

**[1] VPC (Virtual Private Cloud)**: tu terreno delimitado en AWS. Todo vive aquí dentro.

**[3] Internet Gateway**: la puerta que conecta tu edificio con internet.

</Col>
<Col>

**[4] Route Tables**: definen las rutas del tráfico dentro de la red.

<Content title="Terraform" subtitle="AWS: VPC [1]">

<Columns>
<Col>

Primero, indicamos a Terraform que usaremos AWS como proveedor:

```hcl
provider "aws" {
  region = "us-east-2"
}

resource "aws_vpc" "default" {
  cidr_block = "10.0.0.0/16"
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = { Name = "Django_VPC" }
}
```

</Col>
<Col>

El segundo bloque define nuestra **red privada** (VPC).

`enable_dns_support` activa la resolución de nombres dentro de la VPC.

`enable_dns_hostnames` asigna nombres DNS internos a las instancias, de modo que podamos usar nombres como `db.internal` en lugar de direcciones IP (mucho más fácil de recordar).

</Col>
</Columns>

</Content>

<Content title="Terraform" subtitle="AWS: Internet Gateway [3]">

<Columns>
<Col>

El Internet Gateway da a los recursos de la VPC acceso a internet (por ejemplo, para actualizar paquetes o exponer una app web):

```hcl
resource "aws_internet_gateway" "default" {
  vpc_id = aws_vpc.default.id

  tags = {
    Name = "Django_IGW"
  }
}
```

</Col>
<Col>

Ojito a `aws_vpc.default.id`. Terraform entiende las dependencias: no puedes crear el gateway sin la VPC primero.

</Col>
</Columns>

</Content>

<Content title="Terraform" subtitle="AWS: Subnets [2]">

Creamos dos subnets públicas en zonas de disponibilidad distintas, para alta disponibilidad:

<Columns>
<Col>

```hcl
resource "aws_subnet" "public_a" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = "10.0.1.0/24"
  availability_zone       = "${var.aws_region}a"
  map_public_ip_on_launch = true

  tags = {
    Name = "Subnet-Public-A"
  }
}
```

</Col>
<Col>

```hcl
resource "aws_subnet" "public_b" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = "10.0.2.0/24"
  availability_zone       = "${var.aws_region}b"
  map_public_ip_on_launch = true

  tags = {
    Name = "Subnet-Public-B"
  }
}
```

</Col>
</Columns>

<Callout>

RDS requiere al menos dos subnets en zonas de disponibilidad diferentes. `map_public_ip_on_launch = true` asegura que las instancias reciban una IP pública automáticamente.

</Callout>

</Content>

<Content title="Terraform" subtitle="AWS: Route Tables [4]">

<Columns>
<Col>

La tabla de rutas da salida a internet a ambas subnets públicas:

```hcl
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.gw.id
  }

  tags = { Name = "RT-Public-Django" }
}
```

Traducción: "si el destino NO está dentro de la VPC (10.0.0.0/16), envíalo a internet por el Internet Gateway".

</Col>
<Col>

```hcl
# Asociar la subnet A con la tabla de rutas
resource "aws_route_table_association" "a" {
  subnet_id      = aws_subnet.public_a.id
  route_table_id = aws_route_table.public.id
}

# Asociar la subnet B con la tabla de rutas
resource "aws_route_table_association" "b" {
  subnet_id      = aws_subnet.public_b.id
  route_table_id = aws_route_table.public.id
}
```

<Callout>

Ambas subnets deben estar asociadas a la tabla de rutas para tener acceso a internet.

</Callout>

</Col>
</Columns>

</Content>

<Content title="Terraform" subtitle="AWS: Security Groups [5] (ingress)">

<Columns>
<Col>

Un grupo de seguridad define qué tráfico entra a nuestras instancias EC2 dentro de la VPC:

```hcl
resource "aws_security_group" "ec2_sg" {
  vpc_id = aws_vpc.default.id

  # Permitir tráfico HTTP desde cualquier lugar
  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

</Col>
<Col>

También se puede añadir una regla que permita conectarnos a la instancia por SSH desde nuestra IP pública.

</Col>
</Columns>

</Content>

<Content title="Terraform" subtitle="AWS: Security Groups [5] (egress)">

<Columns split="3fr 2fr">
<Col>

Las reglas de salida (egress) controlan el tráfico desde nuestras instancias hacia otros destinos, como internet:

```hcl
resource "aws_security_group" "ec2_sg" {
  vpc_id = aws_vpc.default.id

  egress {
    from_port   = 0
    to_port     = 65535
    protocol    = "-1"              # Todos los protocolos
    cidr_blocks = ["0.0.0.0/0"]     # Cualquier destino en la red
  }
}
```

</Col>
<Col>

Aquí `ingress` y `egress` aparecen por separado para mayor claridad. En la práctica, ambas reglas se definen dentro del mismo recurso.

</Col>
</Columns>

</Content>

<Content title="Terraform" subtitle="AWS: EC2 Instance [6] (roles IAM)">

<Columns>
<Col>

Nuestra instancia EC2 necesita permisos para descargar imágenes Docker desde ECR. Para ello creamos un rol IAM (`aws_iam_role`) que la instancia puede asumir.

El rol otorga credenciales temporales con los permisos necesarios.

</Col>
<Col>

```hcl
resource "aws_iam_role" "ec2_ecr" {
  name = "ec2_ecr_access"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Action = "sts:AssumeRole"
      Effect = "Allow"
      Principal = { Service = "ec2.amazonaws.com" }
    }]
  })
}
```

</Col>
</Columns>

</Content>

<Content title="Terraform" subtitle="AWS: EC2 Instance [6] (políticas y perfil)">

Adjuntamos al rol una política de solo lectura en ECR y creamos el perfil de instancia que EC2 usará al iniciarse:

```hcl
resource "aws_iam_role_policy_attachment" "ecr_read" {
  role       = aws_iam_role.ec2_ecr.name
  policy_arn = "arn:aws:iam::aws:policy/AmazonEC2ContainerRegistryReadOnly"
}

resource "aws_iam_instance_profile" "ec2_profile" {
  name = "ec2_profile"
  role = aws_iam_role.ec2_ecr.name
}
```

`aws_iam_role_policy_attachment` da permisos de solo lectura a ECR: los mínimos, por seguridad.

`aws_iam_instance_profile` permite que la instancia EC2 use el rol del paso anterior.

<Columns split="2fr 1fr">
<Col>

```hcl
  associate_public_ip_address = true

  user_data = <<-EOF

  EOF

  tags = { Name = "Servidor-Django-Andres" }
}
```

La instancia usa el rol IAM configurado para obtener acceso de solo lectura a ECR.

<Content title="Terraform" subtitle="AWS: en resumen…">

Acabas de definir la infraestructura AWS para desplegar tu aplicación Django en un contenedor:

**Redes**: una VPC con DNS interno. Una subred pública en `us-east-2a` que asigna IPs públicas. El Internet Gateway conecta la VPC a internet, y la tabla de rutas envía todo el tráfico no local (`0.0.0.0/0`) al gateway.

**Seguridad**: el security group actúa como firewall: deja entrar HTTP (puerto 80) desde cualquier origen y permite toda la salida. Un rol IAM con la política `AmazonEC2ContainerRegistryReadOnly`, asociado vía instance profile, da acceso a ECR sin credenciales en el código.

**Servidor**: una `t3.micro` con Amazon Linux 2023 (`ami-0c101f26f147fa7fd`). Su `user_data` instala Docker, se autentica en ECR con el rol IAM y levanta el contenedor Django.

</Content>

<Focus>_Tangente_: la seguridad es importante.</Focus>

<Content title="Terraform" subtitle="AWS KMS: cifrar las credenciales">

<Columns>
<Col>

Crea un archivo con las credenciales sensibles, en este caso `db-creds.yml`:

```yaml
username: root
password: password123
```

Cífralo con AWS CLI y la clave KMS:

```bash
aws kms encrypt \
      --key-id <KEY_ID> \
      --region us-east-2 \
      --plaintext fileb://db-creds.yml \
      --output text \
      --query CiphertextBlob > db-creds.yml.enc
```

</Col>
<Col>

Reemplaza `<KEY_ID>` con el ID de tu clave. Si tu archivo YAML tiene otro nombre, cámbialo también en el comando.

El comando genera el archivo cifrado `db-creds.yml.enc`. Puedes compartirlo de forma segura e incluso incluirlo en los repositorios internos de tu empresa (¿recuerdas que añadimos archivos al `.gitignore`?).

<Content title="Django" subtitle="DisallowedHost">

Este error es una medida de seguridad de Django: por defecto, solo acepta peticiones desde localhost. Al acceder desde una IP pública, Django la rechaza.

**La solución** es indicar explícitamente qué dominios o IPs pueden acceder a la aplicación:

1. Abre el archivo `proyecto1/settings.py`.
2. Busca la línea `ALLOWED_HOSTS`.
3. Añade la IP pública de tu instancia EC2 entre comillas. Para permitir cualquier host (no recomendado en producción), usa un asterisco.

```python
ALLOWED_HOSTS = ["XX.XXX.XX.XXX", "*"] # Escribe la IP pública de tu instancia EC2 aquí
```

<Callout title="Importante">

Después del cambio, reconstruye la imagen de Docker, súbela a ECR y vuelve a ejecutar `terraform apply`, para que el servidor EC2 descargue la nueva versión.

</Callout>

<Section>Herramienta #4: AWS RDS</Section>

<Content title="AWS RDS" subtitle="De SQLite a PostgreSQL">

<Columns>
<Col>

Hasta ahora, Django ha usado SQLite, una base de datos en un solo archivo. Sirve para desarrollo, pero **no para producción**:

- No soporta alta concurrencia (varios usuarios a la vez).
- El archivo vive dentro del contenedor, así que **se pierde si el contenedor se reinicia o se reemplaza**.

</Col>
<Col>

**La solución** es un servicio de base de datos gestionado como Amazon RDS:

- Copias de seguridad, parches y escalado sencillo.
- Funciona de forma independiente del servidor de la aplicación (EC2).
- Alta disponibilidad y durabilidad de los datos.

</Col>
</Columns>

</Content>

<Content title="AWS RDS" subtitle="El plan">

1. Crear `database.tf` para definir una instancia PostgreSQL en RDS.
2. Actualizar `settings.py` para que Django se conecte a RDS.
3. Pasar las credenciales de la base de datos al contenedor Docker de forma segura.

</Content>

<Content title="AWS RDS" subtitle="Terraform (subnet)">

<Columns>
<Col>

En `database.tf` definimos primero la red de RDS. RDS necesita un grupo de subnets en al menos dos zonas de disponibilidad (_availability zones_):

```hcl
resource "aws_db_subnet_group" "default" {
  name       = "django-db-subnet-group"
  subnet_ids = [
    aws_subnet.public.id,       // subnet #1
    aws_subnet.public_b.id,     // subnet #2
  ]
}
```

</Col>
<Col>

Cada subnet está en una zona distinta (`a` y `b`). Si una zona falla, RDS puede seguir operando en la otra.

</Col>
</Columns>

</Content>

<Content title="AWS RDS" subtitle="Terraform (security group)">

<Columns split="3fr 2fr">
<Col>

```hcl
resource "aws_security_group" "rds_sg" {
  name   = "django-rds-sg"
  vpc_id = aws_vpc.default.id

  ingress {
    from_port   = 5432
    to_port     = 5432
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"] // Desarrollo: cualquier IP
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

</Col>
<Col>

Un grupo de seguridad que solo admite conexiones entrantes en el puerto de PostgreSQL (5432).

<Callout>

En producción, reemplaza `0.0.0.0/0` por la IP del servidor EC2.

</Callout>

</Col>
</Columns>

</Content>

<Content title="AWS RDS" subtitle="Terraform (instancia de la base de datos)">

Definimos la instancia de PostgreSQL con `aws_db_instance`:

```hcl
resource "aws_db_instance" "default" {
  engine               = "postgres"
  instance_class       = "db.t3.micro"
  db_name              = "django_db"
  username             = "admin"
  password             = var.db_password
  publicly_accessible  = true // Solo para migraciones desde local
}
```

Algunos detalles que vale la pena mencionar:

- La instancia usa el **subnet group y el security group** que creamos antes.
- `publicly_accessible = true` permite ejecutar migraciones desde tu ordenador; en producción debe ser `false`.
- `db_password` debe manejarse como _secret_ (ver la sección de secretos de Terraform).

</Content>

<Section>Herramienta #5: Amazon Cloudwatch</Section>

<Content title="Cloudwatch" subtitle="¿Por qué centralizar los logs?">

<Columns>
<Col>

Por defecto, los logs de la aplicación (stdout y stderr) se guardan dentro del contenedor. Esto trae varios problemas:

- Si el contenedor se detiene o se reemplaza, los logs se pierden.
- Tendrías que conectarte por SSH y ejecutar `docker logs <id>`.
- Repetirlo en varios servidores es impráctico.

**La solución** es enviar los logs a un servicio centralizado, como **Amazon CloudWatch**.

</Col>
<Col>

<Figure src={cloudwatchDiagram} alt="Los contenedores envían sus logs a CloudWatch" />

</Col>
</Columns>

</Content>

<Content title="Cloudwatch" subtitle="1. Configurar Docker">

Docker envía los logs directamente a CloudWatch con el log driver `awslogs`.

Actualiza el `docker run` del script `user_data` en `main.tf`:

```bash
docker run -d -p 80:8080 --restart unless-stopped \
  --log-driver=awslogs \
  --log-opt awslogs-region=us-east-2 \
  --log-opt awslogs-group="django-app-logs" \
  --log-opt awslogs-create-group=true \
  # ... resto de variables -e ...
```

</Content>

<Content title="Cloudwatch" subtitle="2. Permisos IAM">

<Columns split="3fr 2fr">
<Col>

```hcl
resource "aws_iam_policy" "cloudwatch_logs" {
  name   = "EC2CloudWatchLogsPolicy"
  policy = jsonencode({
    Version   = "2012-10-17",
    Statement = [{
      Effect   = "Allow",
      Action   = ["logs:CreateLogStream", "logs:PutLogEvents"],
      Resource = "arn:aws:logs:*:*:*"
    }]
  })
}

resource "aws_iam_role_policy_attachment" "ec2_logs" {
  role       = aws_iam_role.ec2_ecr.name
  policy_arn = aws_iam_policy.cloudwatch_logs.arn
}
```

</Col>
<Col>

El servidor necesita permiso para escribir en CloudWatch. Creamos una política IAM y la adjuntamos al rol de la instancia EC2.

</Col>
</Columns>

</Content>

<Content title="Terraform" subtitle="Destrucción de recursos">

Cuando termines el proyecto, ejecuta:

```bash
terraform destroy
```

Terraform elimina los recursos en orden inverso: primero la instancia EC2, luego los Security Groups, las Route Tables, las Subnets, el Internet Gateway y por último la VPC.

**AWS cobra por los recursos activos**, aunque no los uses. Una instancia EC2 cuesta unos $0.01 por hora (cerca de $7 al mes), y una IP elástica reservada sin uso, unos $0.005 por hora. **Destruye siempre lo que no uses.**

<Callout title="Tip">

`terraform plan -destroy` muestra qué se eliminará antes de destruir nada.

</Callout>

</Content>

<Section>Herramienta #6: nginx</Section>

<Content title="nginx" subtitle="Proxy inverso">

No conviene exponer Gunicorn directamente a internet. Gunicorn ejecuta Django, pero no está optimizado para tráfico HTTP, archivos estáticos ni SSL. Para eso usamos un _reverse proxy_ como nginx.

<Figure src={diagram} alt="nginx recibe el tráfico, sirve los estáticos y reenvía el resto a Gunicorn" />

</Content>

<Content title="nginx" subtitle="nginx y Gunicorn">

<Columns>
<Col>

**nginx** (reverse proxy y archivos estáticos):

- Recibe el tráfico público en el puerto 80 (HTTP).
- Sirve los archivos estáticos (`/static/`).
- Reenvía las peticiones dinámicas a Gunicorn (`proxy_pass`).

</Col>
<Col>

**Gunicorn** (servidor de aplicación WSGI):

- Ejecuta la aplicación Django.
- Escucha en un puerto local no expuesto (`127.0.0.1:8000`), solo accesible para nginx.
- Gestiona los procesos _worker_ de Python.

</Col>
</Columns>

</Content>

<Content title="nginx" subtitle="1. Configurar STATIC_ROOT en Django">

Para que nginx sirva los archivos estáticos, Django los agrupa en un directorio. En `proyecto1/settings.py`, define dónde `collectstatic` debe reunirlos:

```python
STATIC_URL = "static/"
STATIC_ROOT = BASE_DIR / "staticfiles"
```

Luego ejecuta:

```bash
uv run python manage.py collectstatic
```

Esto genera la carpeta `staticfiles`.

</Content>

<Content title="nginx" subtitle="2. Crear el archivo nginx.conf">

<Columns split="2fr 3fr">
<Col>

`nginx.conf` configura nginx para servir directamente los **archivos estáticos** de `collectstatic` (cuando el usuario accede a `/static/`) y reenviar el **resto de las solicitudes** a Gunicorn, como las páginas de tu aplicación Django.

</Col>
<Col>

```nginx
server {
    listen 80;

    location /static/ {
        alias /app/staticfiles/;
    }

    # Redirigir todas las demás solicitudes a Gunicorn
    location / {
        proxy_pass http://127.0.0.1:8000;

        # Enviar encabezados importantes al servidor de aplicación
        proxy_set_header Host $host;
    }
}
```

</Col>
</Columns>

</Content>

<Content title="nginx" subtitle="3. Un entrypoint.sh que inicie ambos servicios">

<Columns split="2fr 3fr">
<Col>

Docker está pensado para un solo proceso principal por contenedor. En producción se recomienda un contenedor para Gunicorn y otro para nginx. **Como estamos en desarrollo**, usaremos un único contenedor para ambos.

En Linux, da permisos de ejecución al script:

```bash
chmod +x entrypoint.sh
```

</Col>
<Col>

```bash
#!/bin/bash
set -e

python manage.py collectstatic --noinput --clear

# Inicia nginx en segundo plano
nginx -g "daemon off;" &

# Inicia Gunicorn como proceso principal
exec gunicorn proyecto1.wsgi:application --bind 127.0.0.1:8000
```

</Col>
</Columns>

</Content>

<Content title="nginx" subtitle="4. Actualizar el Dockerfile y 5. los puertos">

<Columns>
<Col>

4. **Actualiza el `Dockerfile`**: instala nginx y copia los nuevos archivos.

```dockerfile
RUN apt-get install -y nginx

# copiar los archivos
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY entrypoint.sh /app/entrypoint.sh

# establecer al entrypoint.sh como punto de entrada
ENTRYPOINT ["/app/entrypoint.sh"]
```

</Col>
<Col>

5. **Cambia el mapeo de puertos en Terraform** para exponer solo los puertos públicos (80/443). En el `user_data` de `aws_instance`, el puerto mapeado debe ser `80:80`:

```bash
# main.tf
docker run -d -p 80:80 --restart unless-stopped \
       # ... (variables de entorno)
```

</Col>
</Columns>

</Content>

<Content title="nginx" subtitle="Desplegar la nueva versión">

Por último, reconstruye la imagen, súbela a ECR y aplica los cambios con Terraform:

```bash
# 1. Construye la nueva imagen Docker
docker build -t proyecto1-ec2 .

# 2. Etiqueta la imagen para tu repositorio ECR
# (Reemplaza YOUR_ECR_REPO_URL con la URL de tu repo)
docker tag proyecto1-ec2:latest YOUR_ECR_REPO_URL:latest

# 3. Sube la imagen a ECR
docker push YOUR_ECR_REPO_URL:latest

# 4. Aplica los cambios de infraestructura (si los hay)
terraform apply --auto-approve
```
